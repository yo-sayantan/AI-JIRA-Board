Setup & Deployment Guide

Everything you need to install the tools, clone the repo, add your Jira token, and get the board running — on Windows, macOS or Linux. Every command is copy-ready.

Reopen this page anytime — it needs nothing running: ./open-guide.sh (macOS/Linux) · double-click open-guide.bat (Windows) · or click the ? button in the board's header when it's up.

What this is

A personal, self-hosted mirror of your Jira board. A background fetcher pulls the tickets assigned to you into a plain data file; a single-file React app renders them — no Jira login, no waiting on the web UI. Three moving parts:

  • The fetch (jira-intern/) — pulls your tickets. Needs one Jira token.
  • The app (dist/index.html) — renders whatever the fetch produced. Needs nothing.
  • The AI intern (ai-intern/, optional) — enriches PR Readiness Reports and writes ticket briefs with a local model by default. Needs no key unless you choose a cloud provider.
Your tokens never enter the repo. They live in one file outside it (~/.cursor/mcp-secrets.env); everything else points at it by path.

Installing the tools

🪟 Windows

Windows 10 / 11

Easiest path: winget, which ships with Windows 11 and modern Windows 10. Run in PowerShell.

winget install -e --id Git.Git
winget install -e --id Docker.DockerDesktop
winget install -e --id OpenJS.NodeJS.LTS      # optional
winget install -e --id Python.Python.3.12     # optional

Then reboot (Docker Desktop needs it), launch Docker Desktop once, and wait for "Engine running". Docker Desktop will enable WSL 2 for you if it isn't already.

No winget? Install each from its download page in the table above. Use PowerShell (not CMD) for the commands on this page — or Git Bash if you prefer bash syntax.
Path note: commands here use ~/ for your home folder. In PowerShell that's $HOME — e.g. $HOME\.cursor\mcp-secrets.env.
🍎 macOS

macOS 12+

Easiest path: Homebrew. Install it first if you don't have it:

/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
brew install git
brew install --cask docker      # Docker Desktop
brew install node               # optional
brew install python@3.12        # optional

Open Docker Desktop once from Applications and wait until the whale icon says "Docker Desktop is running". Git may also come from Xcode Command Line Tools: xcode-select --install.

🐧 Linux

Linux (Debian / Ubuntu shown)

sudo apt update
sudo apt install -y git curl python3      # python optional

Docker Engine + Compose plugin, via Docker's official convenience script:

curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"      # run docker without sudo
newgrp docker                        # apply the group now (or log out/in)

Node.js (optional) via nvm:

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
nvm install 26      # or any version >= 22.12; the repo's .nvmrc says 26

Fedora/RHEL: swap apt for dnf. Arch: sudo pacman -S git docker docker-compose nodejs.

git pull                       # get the latest changes

Configure — two files, once

1

Create your secrets file

macOS / Linux:

mkdir -p ~/.cursor
cp setup/mcp-secrets.env.template ~/.cursor/mcp-secrets.env
chmod 600 ~/.cursor/mcp-secrets.env

Windows (PowerShell):

New-Item -ItemType Directory -Force "$HOME\.cursor" | Out-Null
Copy-Item "setup\mcp-secrets.env.template" "$HOME\.cursor\mcp-secrets.env"

Now open that file and set at least these two lines:

JIRA_URL=https://jira.your-company.example
JIRA_PERSONAL_TOKEN=your-token-here
2

Create your personal config

Your identity and company URLs live outside the repo, at ~/.ai/config.json, so they never enter git.

macOS / Linux:

mkdir -p ~/.ai
cp setup/config.example.json ~/.ai/config.json
chmod 600 ~/.ai/config.json

Windows (PowerShell):

New-Item -ItemType Directory -Force "$HOME\.ai" | Out-Null
Copy-Item "setup\config.example.json" "$HOME\.ai\config.json"

Edit it — your name exactly as Jira shows it (that's how "assigned to me" matches), your company URLs, and the footer branding. Every key is documented in jira-intern/CONFIG.md. No tokens go in this file.

Config precedence: tracked defaults from config/jira-board.config.json, then a sparse $AI_CONFIG_FILE or ~/.ai/config.json override, then saved runtime Settings. Check with node jira-intern/local-runner/config.mjs path.
3

Local AI model catalog

Every local LLM the intern can run — Ollama tags and direct GGUF downloads — lives in ai-intern/models.json. Settings and this guide both read that file. When a new model ships, add an object there (see the howto field at the top of the file) and restart AI-Intern.

Host Ollama (Settings checkbox on): install, pull, where files live. Checkbox off: download a GGUF, where to place it, how to register it.

Docker — build & deploy

The one command

docker compose up -d --build

Then open http://localhost:4321/dist/index.html ✓

This builds the board image (stage 1 compiles the app, stage 2 runs the server + Python fetch) and starts Compose project JIRA-Project with three containers: JIRA-Board (the board), AI-Ollama (local models) and AI-Intern (report enrichment). It mounts your ~/.cursor and ~/.ai folders read-only, fetches once on boot, and then refreshes on the cadence you choose in Settings → Background jobs (defaults: active tickets twice a day, whole board and PR reports twice a week). There is no fixed timer.

Board only, without the AI pair (Settings then shows "AI intern offline"):

docker compose up -d --build jira-board
Loopback by default. The port is published on 127.0.0.1 only. To reach the board from another device, publish it on the LAN and tell the server which host names it may answer to (it rejects unknown Host headers with 403 to block DNS rebinding): BIND_IP=0.0.0.0 ALLOWED_HOSTS=my-laptop.local,192.168.1.20 docker compose up -d
Linux hosts: the board runs as user id 1000 inside the container, so the bind-mounted data folder must be writable by it — once: sudo chown -R 1000:1000 ./jira-intern. Docker Desktop (macOS / Windows) handles this for you.

Build and start separately

# build the images only (no --pull: Docker Hub can be slow; add it when you want fresh base images)
docker compose build
# start what was built
docker compose up -d

Stick with Compose rather than a hand-written docker run: it wires the three services together, publishes only the board port, and mounts the directories ~/.cursor → /home/node/.cursor and ~/.ai → /home/node/.ai read-only (a single-file bind mount keeps pointing at the old inode after an editor rewrites mcp-secrets.env). docker-compose.yml is commented line by line if you need to adapt it.

Managing the container

docker compose logs -f          # watch fetch + server logs
docker compose ps               # is it running?
docker compose restart          # restart without rebuilding
docker compose down             # stop and remove
docker compose up -d --build    # rebuild + redeploy after a code change
docker exec -it JIRA-Board sh   # shell inside the container
docker stats JIRA-Board         # resource usage
docker image prune -f           # clean old layers
Changed anything in src/? You must rebuild (--build) — the app is baked into the image. Changing only data needs no rebuild; the container refetches on its own.

AI Intern — local & cloud models

Three containers, one command

docker compose up -d --build starts project JIRA-Project with JIRA-Board (fetch + UI), AI-Ollama (local models), and AI-Intern (report enrichment, ticket briefs, model download). All three stay up with restart: unless-stopped. Refresh and Regenerate honour Settings — you do not need a host terminal for AI. The AI pair is optional: docker compose up -d --build jira-board runs the board alone and reports stay deterministic.

Settings → AI usage: None / Low / Moderate / Max, then Local or Cloud. Max is the product name for the stored value full (longest timeout). Local models are a dropdown. If the chosen tag is already on disk, that is enough. If it is not, the download icon beside the list queues a pull. The ? next to the list opens the matching section below: Host Ollama when that checkbox is on, otherwise the GGUF download / place / trigger path.

The catalog of every local LLM (tags + download links) is ai-intern/models.json — add a row there when a new model is released. Jump: Host Ollama · GGUF files.

Host Ollama — install, pull, deploy

When the Host Ollama checkbox is on

Settings → Local AI → tick Host Ollama. The intern then talks to Ollama.app on this Mac (Metal) at host.docker.internal:11434 instead of the Linux Docker VM (CPU). Use this for 14B+ if you can, and for every 32B / 70B tag.

1

Install Ollama and leave it running

Download Ollama.app, open it once, and keep it in the menu bar. First-run will listen on 127.0.0.1:11434.

2

Pull a model (or let Settings do it)

Easiest: pick the tag in Settings and click the download icon. Same thing from a terminal:

ollama pull qwen2.5-coder:7b

Weights land in ~/.ollama/models. Do not copy blobs into that tree by hand — Ollama owns it. Catalog: ollama.com/library. Default tag: qwen2.5-coder:7b.

3

Trigger it from the board

Host Ollama on, model selected (no download icon once it is installed), AI usage not None. Then Regenerate a PR report or Refresh — AI-Intern enqueues enrichment against that tag. Idle status in Settings should read Idle · local · <tag>.

2

Where to place it

Save the file in jira-intern/models/ (git-ignored) or Downloads. Ollama will not see it there until you register it.

mkdir -p jira-intern/models
# move the downloaded .gguf in here, e.g.
# mv ~/Downloads/qwen2.5-coder-7b-instruct-q4_k_m.gguf jira-intern/models/
3

Register the tag (how to trigger)

In-container (Host Ollama off) — copy into the Ollama container, then create with the Settings tag:

docker cp jira-intern/models/qwen2.5-coder-7b-instruct-q4_k_m.gguf AI-Ollama:/tmp/model.gguf
docker exec AI-Ollama sh -c 'printf "FROM /tmp/model.gguf\n" > /tmp/Modelfile && ollama create qwen2.5-coder:7b -f /tmp/Modelfile'

Created blobs live on volume jira-ai-models (/root/.ollama inside the container).

Host Ollama — same file, then:

cat > /tmp/Modelfile <<'EOF'
FROM /absolute/path/to/qwen2.5-coder-7b-instruct-q4_k_m.gguf
EOF
ollama create qwen2.5-coder:7b -f /tmp/Modelfile

That writes into ~/.ollama/models. Tick Host Ollama so the intern uses it.

Then from the board: Settings → pick the matching tag (download icon disappears once the tag exists) → AI usage not None → Regenerate / Refresh. The intern enqueues the job; you do not need a host console.

Add a newly released model

Edit ai-intern/models.json. Copy an existing object, set id / pull to the Ollama tag you will ollama create or ollama pull, fill ollama (library URL) and gguf (direct .gguf URL), then restart the intern:

docker compose up -d --build jira-ai

The Settings dropdown and both tables on this page pick up the new row from that file. No UI change is required.

What the AI can and cannot see. Every model — local or cloud — reads the intern volume plus live Jira/Bitbucket REST with your tokens. The CI, Checkmarx and Dynatrace proof rows are filled only when their optional keys and endpoints are configured (BITBUCKET_PAT for build status; CHECKMARX_API_KEY + endpoints.checkmarxBase; DYNATRACE_PAT + endpoints.dynatraceTenants — see jira-intern/CONFIG.md). Without them those rows read Not read / Not verified and are shown as gaps, never guessed.

Other ways to run

📄 Static file — no server

The build is one self-contained HTML file. If a data dump exists, just open it:

# macOS
open dist/index.html
# Linux
xdg-open dist/index.html
# Windows
start dist\index.html

Press r to re-read the latest data.

🖥️ Live local server

The header button becomes a real Refresh that runs the fetch on your machine.

npm install
npm run serve

Serves on 127.0.0.1:4321. Needs Node.js 22.12+ and Python 3.11+.

Build & develop the app

npm install        # install dependencies
npm run dev        # localhost:5173 — sample data, hot reload
npm run typecheck  # tsc --noEmit
npm test           # Python suite + vitest suite
npm run build      # → dist/index.html (single file)

Refresh the ticket data by hand

bash jira-intern/local-runner/run-intern.sh        # active tickets (daily)
bash jira-intern/local-runner/update-completed.sh  # full Completed archive (weekly)

Both rewrite jira-intern/data.json and data.js; reload the board to see the result.

SymptomFix
Board loads but is emptyNo data yet. Wait for the boot fetch, check docker compose logs -f, or run the fetch by hand.
"no JIRA_PERSONAL_TOKEN found — skipping fetch"Your secrets file isn't mounted or readable. Confirm ~/.cursor/mcp-secrets.env exists and contains the token.
docker: cannot connect to the Docker daemonDocker Desktop isn't running. Launch it and wait for "Engine running".

Privacy & data

Everything stays on your machine by default. Your tickets, comments, PR metadata and reports are written to jira-intern/ (git-ignored) and nowhere else. The only network calls are to your own Jira, Bitbucket and Confluence, with your tokens, over verified TLS.

Local AI (the default) sends ticket text to Ollama inside Docker or on this machine — still nothing leaves it. Cloud AI is a choice you make in Settings: the AI-Intern then sends the ticket title, description, comments, acceptance criteria, PR metadata, changed-file paths (not diffs) and the base report to the provider you picked — Claude, Gemini or Cursor — under your own key. Cursor Cloud Agents run in agent mode; prefer Local AI or the Claude/Gemini chat APIs for sensitive tickets.

No cookies, no analytics, no telemetry, no external fonts or scripts. The board keeps your appearance, notification and feature choices, manual archive moves and acceptance-criteria ticks in the browser's localStorage; job and AI choices also go to jira-intern/.settings.json when the server runs. The server listens on loopback unless you opt in to the LAN. Full detail: docs/SECURITY.md.
