What this is

A personal, self-hosted mirror of your Jira board. A background fetcher pulls the tickets assigned to you into a plain data file; a single-file React app renders them — no Jira login, no waiting on the web UI. Two moving parts:

  • The fetch (jira-intern/) — pulls your tickets. Needs one Jira token.
  • The app (dist/index.html) — renders whatever the fetch produced. Needs nothing.
Your tokens never enter the repo. They live in one file outside it (~/.cursor/mcp-secrets.env); everything else points at it by path.

Installing the tools

🪟 Windows

Windows 10 / 11

Easiest path: winget, which ships with Windows 11 and modern Windows 10. Run in PowerShell.

winget install -e --id Git.Git
winget install -e --id Docker.DockerDesktop
winget install -e --id OpenJS.NodeJS.LTS      # optional
winget install -e --id Python.Python.3.12     # optional

Then reboot (Docker Desktop needs it), launch Docker Desktop once, and wait for "Engine running". Docker Desktop will enable WSL 2 for you if it isn't already.

No winget? Install each from its download page in the table above. Use PowerShell (not CMD) for the commands on this page — or Git Bash if you prefer bash syntax.
Path note: commands here use ~/ for your home folder. In PowerShell that's $HOME — e.g. $HOME\.cursor\mcp-secrets.env.
🍎 macOS

macOS 12+

Easiest path: Homebrew. Install it first if you don't have it:

/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
brew install git
brew install --cask docker      # Docker Desktop
brew install node               # optional
brew install python@3.12        # optional

Open Docker Desktop once from Applications and wait until the whale icon says "Docker Desktop is running". Git may also come from Xcode Command Line Tools: xcode-select --install.

🐧 Linux

Linux (Debian / Ubuntu shown)

sudo apt update
sudo apt install -y git curl python3      # python optional

Docker Engine + Compose plugin, via Docker's official convenience script:

curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"      # run docker without sudo
newgrp docker                        # apply the group now (or log out/in)

Node.js (optional) via nvm:

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
nvm install 20

Fedora/RHEL: swap apt for dnf. Arch: sudo pacman -S git docker docker-compose nodejs.

Verify everything is installed

git --version
docker --version
docker compose version
node --version     # optional
python3 --version  # optional (Windows: python --version)

Each should print a version. If docker errors with "cannot connect to the daemon", Docker Desktop isn't running yet.

Getting the code — Git commands

Clone the repository

git clone https://github.com/yo-sayantan/AI-JIRA-Board.git
cd AI-JIRA-Board

First time using Git on this machine? Set your identity:

git config --global user.name  "Your Name"
git config --global user.email "you@example.com"

Everyday Git

git pull                       # get the latest changes
git status                     # what have I changed?
git switch -c my-change        # start a branch
git add -A                     # stage everything
git commit -m "What I changed" # commit
git push -u origin my-change   # push the branch
Never commit secrets. .gitignore already blocks *.env and the fetched ticket data. Before pushing, a quick sanity check: git status should show no .env files and no jira-intern/data.*.

Configure — two files, once

1

Create your secrets file

macOS / Linux:

mkdir -p ~/.cursor
cp setup/mcp-secrets.env.template ~/.cursor/mcp-secrets.env
chmod 600 ~/.cursor/mcp-secrets.env

Windows (PowerShell):

New-Item -ItemType Directory -Force "$HOME\.cursor" | Out-Null
Copy-Item "setup\mcp-secrets.env.template" "$HOME\.cursor\mcp-secrets.env"

Now open that file and set at least these two lines:

JIRA_URL=https://jira.your-company.example
JIRA_PERSONAL_TOKEN=your-token-here
2

Create your personal config

Your identity and company URLs live outside the repo, at ~/.ai/config.json, so they never enter git.

macOS / Linux:

mkdir -p ~/.ai
cp setup/config.example.json ~/.ai/config.json
chmod 600 ~/.ai/config.json

Windows (PowerShell):

New-Item -ItemType Directory -Force "$HOME\.ai" | Out-Null
Copy-Item "setup\config.example.json" "$HOME\.ai\config.json"

Edit it — your name exactly as Jira shows it (that's how "assigned to me" matches), your company URLs, and the footer branding. Every key is documented in docs/CONFIG.md. No tokens go in this file.

Config precedence: tracked defaults from config/jira-board.config.json, then a sparse $AI_CONFIG_FILE or ~/.ai/config.json override, then saved runtime Settings. Check with node jira-intern/local-runner/config.mjs path.
3

Local AI model catalog

Every local LLM the intern can run — Ollama tags and direct GGUF downloads — lives in ai-intern/models.json. Settings and this guide both read that file. When a new model ships, add an object there (see the howto field at the top of the file) and restart AI-Intern.

Host Ollama (Settings checkbox on): install, pull, where files live. Checkbox off: download a GGUF, where to place it, how to register it.

Docker — build & deploy

The one command

docker compose up -d --build

Then open http://localhost:4321/dist/index.html ✓

This builds the image (stage 1 compiles the app, stage 2 runs the server + Python fetch), starts Compose project JIRA-Project with container JIRA-Board, mounts your secrets read-only, fetches once on boot, and re-fetches every 15 minutes.

Build and run separately

# build the image only
docker compose build --pull
# or with plain docker
docker build -t jira-board:latest .

# run it (plain docker, without compose)
docker run -d --name JIRA-Board -p 4321:4321 \
  -v "$HOME/.cursor/mcp-secrets.env:/root/.cursor/mcp-secrets.env:ro" \
  -v "$(pwd)/jira-intern:/app/jira-intern" \
  jira-board:latest

Windows PowerShell equivalent for the volume flags: -v "${HOME}\.cursor\mcp-secrets.env:/root/.cursor/mcp-secrets.env:ro" and -v "${PWD}\jira-intern:/app/jira-intern".

Managing the container

docker compose logs -f          # watch fetch + server logs
docker compose ps               # is it running?
docker compose restart          # restart without rebuilding
docker compose down             # stop and remove
docker compose up -d --build    # rebuild + redeploy after a code change
docker exec -it JIRA-Board sh   # shell inside the container
docker stats JIRA-Board         # resource usage
docker image prune -f           # clean old layers
Changed anything in src/? You must rebuild (--build) — the app is baked into the image. Changing only data needs no rebuild; the container refetches on its own.

One-click launcher (macOS / Linux)

Starts Docker if needed, frees the port, rebuilds, redeploys, waits for health, and opens the board. Safe to run repeatedly — it never stacks containers or drifts ports.

AI Intern — local & cloud models

Two containers, one command

docker compose up -d --build starts project JIRA-Project with JIRA-Board (fetch + UI), AI-Ollama, and AI-Intern (report enrichment, ticket briefs, model download). Both stay up with restart: unless-stopped. Refresh and Regenerate honour Settings — you do not need a host terminal for AI.

Settings → AI usage: None / Low / Moderate / Max, then Local or Cloud. Max is the product name for the stored value full (longest timeout). Local models are a dropdown. If the chosen tag is already on disk, that is enough. If it is not, the download icon beside the list queues a pull. The ? next to the list opens the matching section below: Host Ollama when that checkbox is on, otherwise the GGUF download / place / trigger path.

The catalog of every local LLM (tags + download links) is ai-intern/models.json — add a row there when a new model is released. Jump: Host Ollama · GGUF files.

Host Ollama — install, pull, deploy

When the Host Ollama checkbox is on

Settings → Local AI → tick Host Ollama. The intern then talks to Ollama.app on this Mac (Metal) at host.docker.internal:11434 instead of the Linux Docker VM (CPU). Use this for 14B+ if you can, and for every 32B / 70B tag.

1

Install Ollama and leave it running

Download Ollama.app, open it once, and keep it in the menu bar. First-run will listen on 127.0.0.1:11434.

2

Pull a model (or let Settings do it)

Easiest: pick the tag in Settings and click the download icon. Same thing from a terminal:

ollama pull qwen2.5-coder:7b

Weights land in ~/.ollama/models. Do not copy blobs into that tree by hand — Ollama owns it. Catalog: ollama.com/library. Default tag: qwen2.5-coder:7b.

3

Trigger it from the board

Host Ollama on, model selected (no download icon once it is installed), AI usage not None. Then Regenerate a PR report or Refresh — AI-Intern enqueues enrichment against that tag. Idle status in Settings should read Idle · local · <tag>.

2

Where to place it

Save the file in jira-intern/models/ (git-ignored) or Downloads. Ollama will not see it there until you register it.

mkdir -p jira-intern/models
# move the downloaded .gguf in here, e.g.
# mv ~/Downloads/qwen2.5-coder-7b-instruct-q4_k_m.gguf jira-intern/models/
3

Register the tag (how to trigger)

In-container (Host Ollama off) — copy into the Ollama container, then create with the Settings tag:

docker cp jira-intern/models/qwen2.5-coder-7b-instruct-q4_k_m.gguf AI-Ollama:/tmp/model.gguf
docker exec AI-Ollama sh -c 'printf "FROM /tmp/model.gguf\n" > /tmp/Modelfile && ollama create qwen2.5-coder:7b -f /tmp/Modelfile'

Created blobs live on volume jira-ai-models (/root/.ollama inside the container).

Host Ollama — same file, then:

cat > /tmp/Modelfile <<'EOF'
FROM /absolute/path/to/qwen2.5-coder-7b-instruct-q4_k_m.gguf
EOF
ollama create qwen2.5-coder:7b -f /tmp/Modelfile

That writes into ~/.ollama/models. Tick Host Ollama so the intern uses it.

Then from the board: Settings → pick the matching tag (download icon disappears once the tag exists) → AI usage not None → Regenerate / Refresh. The intern enqueues the job; you do not need a host console.

Add a newly released model

Edit ai-intern/models.json. Copy an existing object, set id / pull to the Ollama tag you will ollama create or ollama pull, fill ollama (library URL) and gguf (direct .gguf URL), then restart the intern:

docker compose up -d --build jira-ai

The Settings dropdown and both tables on this page pick up the new row from that file. No UI change is required.

Honest gap. Local models (including Gemma / GPT-OSS / nano) read the intern volume and live Jira/Bitbucket REST (same tokens as Cursor MCP). CI, Checkmarx and live Dynatrace stay Not verified until dedicated REST is added.

Other ways to run

The build is one self-contained HTML file. If a data dump exists, just open it:

# Linux
xdg-open dist/index.html

start dist\index.html

Press r to re-read the latest data.

🖥️ Live local server

The header button becomes a real Refresh that runs the fetch on your machine.

npm install
npm run serve

Serves on port 4321. Needs Node.js 20+.

Build & develop the app

npm install        # install dependencies
npm run dev        # localhost:5173 — sample data, hot reload
npm run typecheck  # tsc --noEmit
npm run build      # → dist/index.html (single file)

Refresh the ticket data by hand

bash jira-intern/local-runner/run-intern.sh        # active tickets (daily)
bash jira-intern/local-runner/update-completed.sh  # full Completed archive (weekly)

Both rewrite jira-intern/data.json and data.js; reload the board to see the result.

FAQ — real problems, real fixes

Every one of these actually happened while building and running this board — so a new user will likely meet some of them too. Click a question to open it.

+ Docker build dies at RUN npm run build — “Unable to resolve @typescript/typescript-linux-arm64” docker

TypeScript 7 ships its native compiler as per-platform optional npm packages. When npm ci runs inside the image over a slow/flaky Docker-VM network, npm silently skips optional packages — then tsc can’t find its Linux binary.

Fix: deploy with ./start-jira-board.sh — it builds dist/ on your machine first and tells Docker to just package it (DIST_SOURCE=prebuilt). Building by hand:

npm run build
docker compose build --build-arg DIST_SOURCE=prebuilt

BuildKit collapses the real error — rerun with docker build --progress=plain . to actually see it.

+ The deploy “hangs” for 10+ minutes with no output docker

Docker Hub pulls can crawl from the Docker VM (~80 KB/s seen here), and --pull re-fetches the base image on every build. The start script deliberately does not use --pull — keep it that way, keep the node base image cached, and never Ctrl-C mid-pull (the download is discarded).

+ I redeployed and the board came up empty data

Compose bind-mounts ./jira-intern from the folder you deploy from — your ticket data lives wherever you last deployed. Deploying from a fresh clone/folder points the container at an empty directory.

Fix: find the old data and copy it over before deploying from the new folder:

docker inspect JIRA-Board --format '{{range .Mounts}}{{.Source}}{{"\n"}}{{end}}'
# then copy data.json, data.js, .state.json, cache/, reports/ from that
# jira-intern/ into the new folder's jira-intern/ and redeploy

Or simply press Refresh board and rebuild the Completed archive — everything is re-fetchable from Jira, it just takes longer.

+ npm ci fails: “Your cache folder contains root-owned files” docker

An old npm bug left root-owned files in ~/.npm. Either fix the ownership (the command npm prints) or sidestep with a throwaway cache:

npm ci --cache "$TMPDIR/npm-cache"
+ The Raised chip is missing (or shows nothing) board

The raised-by-me list is fetched by the board refresh — a brand-new deployment has none yet. Click Refresh board once (or the Hard refresh button inside the Raised view). The chip hides itself while the list is empty, and the whole feature can be toggled in Settings → Raised by me.

+ AI briefs aren’t appearing on tickets board

Three usual causes, in order: Settings → AI usage is set to None (deterministic mode — no briefs by design); the AI-Intern container is down (Settings shows its health); or it simply hasn’t gotten there yet — the summarize pass writes up to 8 briefs per run, so a full board fills in over a few scheduled passes. Raised tickets queue after active ones.

+ “Jira MCP unavailable — showing last known state” / fetch keeps failing network

Either the VPN is down (on-prem Jira is only reachable on it) or the token expired (Jira returns 401). Check the token file and test it directly:

curl -sk -H "Authorization: Bearer $JIRA_PERSONAL_TOKEN" \
  "$JIRA_URL/rest/api/2/myself" | head -c 200

A JSON blob with your name = token fine, look at the VPN. HTML or 401 = make a new Personal Access Token and update ~/.cursor/mcp-secrets.env.

+ “Skipped — another refresh/archive was already running” data

Only one job may write data.json at a time (lock files keep the daily fetch, the archive rebuild, per-ticket refreshes and the raised refresh apart). Wait for the running job — the header button shows its live progress. A stale lock from a killed run clears itself once its owner process is gone.

+ A ticket’s PR badge looks stale (merged PR still shows open) data

Review activity happens in Bitbucket and never bumps the Jira ticket’s “updated” time, so the fast path can carry an old badge. Use the per-ticket refresh button on the card (or in its drawer). If Bitbucket itself is unreachable, PR data is deliberately carried forward rather than wiped — the run note in the footer says so.

+ Port 4321 is already in use network

./start-jira-board.sh reclaims the port automatically (it stops whatever holds it, including stale containers from older compose projects). Manual alternatives:

docker compose down
PORT=8080 docker compose up -d --build   # or run on another port
